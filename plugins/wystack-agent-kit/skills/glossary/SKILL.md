# Glossary

Create a term only when its meaning affects product behavior, architecture, or communication. Generic programming vocabulary does not need a project definition.

Follow the user's template and the project's existing glossary convention. With neither, preserve only what the term needs:

- canonical name;
- one precise definition;
- aliases to use or avoid when ambiguity is real;
- relationships, examples, or counterexamples that sharpen the boundary.

Keep one authoritative definition and make other artifacts reference it rather than restating it. When a rename changes code, APIs, or accepted documents, surface that impact before applying the wider migration.

Complete when the term distinguishes itself from its nearest neighbor and a reader can apply it consistently in a new scenario.
