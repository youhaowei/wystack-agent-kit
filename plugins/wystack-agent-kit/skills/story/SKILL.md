# Story

Follow the user's template or the project's existing story convention.

A story owns one requirement: the actor or affected user, goal, value, observable acceptance behavior, and scenarios that clarify meaningful edges. It does not own architecture, implementation tasks, or an estimate.

Keep it valuable and testable. If the requirement contains several independently useful outcomes, split it; if a fragment has no value alone, merge it back. Use the project's domain vocabulary consistently.

Complete when a product reviewer can decide whether the requirement is satisfied without knowing how it was implemented.
